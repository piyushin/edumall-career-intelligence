# R20-C2c Verification

## Scope delivered

R20-C2c completes report-credit operations on top of the C2a commerce core and the C2b admin UI. It adds one additive migration (`20260913020000_r20_c2c_credit_operations`), a derived-principal unlock service, atomic organization → counsellor transfers, bulk unlock, staff self-service credit purchase, and the real Report Credits workspace that replaces the C2b interim page. No scientific or report-generation code changes; automatic generation and the free short result are untouched.

### Accounting rule (authoritative)

**One report credit = one full-report access grant for one assessment attempt to one principal** (candidate/user, organization, counsellor/user). The ledger now records the consumption principal (`principal_key`: `ORGANIZATION:<id>`, `USER:<id>`, `CANDIDATE:<id>`), and the per-wallet consumption uniqueness index is `(wallet_id, attempt_id, principal_key)`, so one wallet may legitimately spend separate credits on separate principals for one attempt but can never charge the same principal twice. A `CHECK` requires a principal on every `CONSUMPTION` row; historical consumptions are backfilled from their linked grant. Sponsored candidate entitlements are linked one-to-one from the ledger (`entitlement_id`, unique). Transfer legs carry a shared `transfer_id` with a unique `(transfer_id, event_type)` index and a check that only transfer legs carry it.

### Backend

- **`ReportUnlockService`** (`POST /staff/report-credits/unlock`, `POST /staff/report-credits/bulk-unlock`, central `POST /admin/report-credits/unlock`). The body names only `attemptId`(s), an explicit `mode` (`ORGANIZATION` | `COUNSELLOR` | `CANDIDATE`) and an optional reference. The source wallet and principal are derived: tenant administrators spend their own organization wallet (modes `ORGANIZATION` or `CANDIDATE`), counsellors spend their own user wallet (mode `COUNSELLOR` only, and only for candidates actively assigned to them in their organization), central administrators name a wallet inside their scope. The attempt must belong to the wallet owner's organization and to the caller's scope, be `SUBMITTED`, and have a `GENERATED` report. Each charge runs in one `SERIALIZABLE` transaction: conditional decrement (`status = ACTIVE AND balance >= 1`), grant or entitlement creation, ledger row referencing that grant/entitlement, grant back-link, audit row. Idempotency is by outcome: an active grant/entitlement for the derived principal, or a prior consumption row for `(wallet, attempt, principal)`, returns `already_granted` and charges nothing. `CANDIDATE` mode upserts the candidate's `REPORT` entitlement with source `TENANT_CREDIT` and leaves organization/counsellor grants untouched; it is skipped as `CANDIDATE_ACCESS_NOT_REQUIRED` for institutional (non-commercial) candidates who already open the full report without an entitlement. Bulk unlock: tenant administrators only, `ORGANIZATION` or `CANDIDATE` mode, 1–200 de-duplicated attempts, one credit per charged attempt, per-item `charged` / `already_granted` / `skipped:<REASON>` plus a summary and closing balance; any unexpected failure rolls back every item, so partial charges are never silent. Counsellor bulk unlock is deferred (see below).
- **Transfers** (`POST /staff/report-credits/transfers` for tenant administrators, `POST /admin/report-credits/transfers` for central administrators naming `sourceWalletId`). Source is the session's organization wallet for tenants. Destination must hold an active `COUNSELLOR` membership in the source organization; the counsellor's user wallet is created on demand. Quantity positive and available (conditional decrement, never negative), `TRANSFER_OUT` + `TRANSFER_IN` with the shared `transferId`, audited, and idempotent on a client `transferKey` (replay returns the existing legs; a reused key with different wallet/quantity is rejected). Cross-tenant transfers are impossible by construction; counsellors and suspended/closed wallets are refused.
- **Wallet directory and control** (central only): `GET /admin/report-credits/wallets` searches organization wallets by name and counsellor/user wallets by name, mobile or email, filtered by owner type/status, with per-wallet stats (purchased, allotted, transferred in/out, consumed, reversed, revoked, remaining). `GET .../wallets/:id`, `GET .../wallets/:id/ledger` (immutable, paginated, with order/attempt/grant/entitlement/transfer evidence and actor), `POST .../allot` (complimentary), `POST .../revoke-unused` (capped by unused administrator-allotted credits), `POST .../status` (suspend/reactivate; close only at zero balance; closed is terminal), `GET /admin/report-credits/organizations/:id/wallet`. Tenant administrators can never mint complimentary credits: allotment, revocation, directory and status are `assertCentralAdministrator`. The legacy `POST .../wallets/:id/consume` now routes through the derived unlock with the wallet owner as the principal.
- **Staff self-service purchase** (`/staff/commerce/*`): `GET credit-packs` lists active `REPORT_CREDIT_PACK` products for the audience derived from the role (`ORGANIZATION` for tenant administrators, `COUNSELLOR` for counsellors), platform-wide or own-organization scope, with backend price/tax/total preview; `POST orders` creates the order with purchaser type, wallet, price, tax and coupon all resolved server-side (`CommercePricingService.resolvePrice` returns the platform price for credit packs regardless of delegation; tenant coupons stay excluded from credit packs); `GET orders`; and the existing Razorpay intent/verify, webhook and manual-payment (`BANK_TRANSFER`/`UPI` reference, central approval, policy-gated) flows are reused unchanged. `OrderFulfilmentService.fulfil` remains the single fulfilment path and creates the `PURCHASE` ledger credit exactly once per order. An organization order may be completed by any administrator of that organization; counsellor orders only by the counsellor.
- Counsellors gain `report.credit.view` in the legacy permission set (own wallet and own unlock only). Candidate 360 exposes the entitlement `source`.

### Web

- **`/admin/report-credits`** (replaces the interim page): searchable, filterable wallet directory with balances and stats; **`/admin/report-credits/[walletId]`**: owner, balance, original purchased/allotted, used, transferred, remaining, status, full paginated ledger and audit evidence, complimentary allotment, revoke-unused, suspend/reactivate/close, and central organization → counsellor transfer. Central-only; tenant sessions are told to use the staff workspace.
- **`/staff/credits`** (new; staff navigation is Reports · Credits): own wallet balance and stats, recent ledger, credit packs for the role's audience with server-resolved price/tax/indicative total, quantity and optional coupon, Razorpay checkout when configured, bank transfer / UPI reference when the organization policy allows manual payment, pending and historical orders, and (tenant administrators) transfer to an active counsellor with a fresh idempotency key per submission. The browser never sends an amount.
- **`/staff/reports` and `/staff/reports/[attemptId]`**: wallet balance in the header; per-row and detail actions **Unlock for organization — 1 credit** and the separate **Sponsor candidate access — 1 credit** for tenant administrators, **Unlock for me — 1 credit** for counsellors. Actions are hidden when the report is not generated, the wallet is suspended/closed or empty, or the principal already has access; the server re-derives every condition. After an unlock the page re-fetches the record and the full report from the server. Tenant administrators can select eligible rows and bulk unlock in exactly one principal mode with the per-item outcome and summary shown.
- **Organization detail** shows the organization wallet (balance, purchased, allotted, transferred out, consumed, status, recent ledger) with a link to the credit workspace; **Candidate 360** labels sponsored candidate access.

## Security / accounting checks

Cross-tenant IDOR (wallet scope and attempt organization are checked inside the transaction), arbitrary wallet selection (staff wallets derived from the session; central wallets scope-checked), arbitrary principal selection (principal derived from role + wallet owner + attempt candidate + explicit mode), double consumption (outcome idempotency + `(wallet, attempt, principal)` unique index), duplicate transfer (`transferKey` replay + unique transfer legs), replay (P2002/P2034 mapped to idempotent replay or a retryable conflict), negative balance (conditional decrement + DB check), suspended/closed wallets (status in the conditional update), stale-balance race (`SERIALIZABLE`), grant without ledger evidence and ledger without grant (created in one transaction with mutual references; the entitlement link is unique). Every mutation writes `AuditLog` inside its transaction.

Run from the repository root:

```text
pnpm lint
pnpm type-check
pnpm --filter @edumall/database test
pnpm --filter @edumall/api test
pnpm --filter @edumall/web test

```

Focused coverage: same-tenant organization → counsellor transfer with shared transfer id; cross-tenant destination denied; source derived from session; insufficient balance without ledger writes; idempotent transfer replay; suspended wallet and counsellor refusal; organization / counsellor / sponsored-candidate unlock each consume exactly one credit and grant only their principal; no entitlement in organization mode and no grant in candidate mode; duplicate unlock not double-charged; unauthorized role/mode rejected; out-of-scope and unassigned attempts skipped; suspended wallet, ungenerated report and empty balance skipped without writes; institutional candidate sponsorship skipped; bulk per-item accounting and summary; credit-pack fulfilment exactly once; staff orders derive purchaser, wallet and platform price from the session and ignore client amounts; C2c migration invariants; web unlock offers respect backend access state, bulk mode restricted to organization/candidate, re-fetch after unlock, self-service order body carries no amount, and navigation. Existing automatic-generation, short-result and access-policy suites are unchanged and green.

## Deferred / remaining

- **Counsellor bulk unlock** is deliberately single-attempt in C2c: bulk would need per-attempt assignment validation from a user wallet across candidates and adds little over the per-row action; the endpoint refuses counsellors explicitly.
- **C2d**: counselling availability/booking/cancellation/no-show, platform counsellor pool, contract grant for a booked counsellor, online/offline session details, notifications; staff navigation gains Counselling.
- Platform items unchanged from C2a: worker sweep for stuck fulfilment; gateway `refund.processed` webhook consumption; credit validity/expiry is not modelled (wallets have no expiry today, so validity is not shown).
